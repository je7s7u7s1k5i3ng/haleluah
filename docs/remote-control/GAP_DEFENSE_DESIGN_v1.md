## 1. 현재 구조 요약 (드라이브 사본 기준)

```
메인 PC (Claude Code)
 ├─(A) JOB 경로:  J:\...\JOB_###.md  ──▶ 보조 PC run_job.vbs → run_job.ps1 → codex exec
 │                결과 → 대상 폴더 / JOB_###_완료.txt | _실패.txt
 └─(B) UI 제어:   WinRM → requests\<run_id>.request.json + 예약작업 CodexRemoteControl_<run_id>
                  → remote_worker(V1.1, UIA 이름기반) → responses\<run_id>.response.json
```
- 장점: **동작은 fail-closed**(모호하면 안 함), 재실행 방지, 좌표 클릭 금지, 증거 해시.
- 결정적 결함: **멈춘 것을 감지·해제·재개하는 장치가 0개.** 락 하나만 남아도 조용히 영구 정지한다.

## 2. 설계 원칙 (새로 추가)

| # | 원칙 | 의미 |
|---|---|---|
| P1 | 동작은 fail-closed, **일정은 fail-forward** | 확실하지 않은 클릭은 안 한다. 대신 그 작업만 보류하고 큐의 다음 작업으로 간다 |
| P2 | 모든 대기에는 **시간 예산** | 무한 대기 0개. 예산 초과 = 실패로 분류 → 사다리(§4) |
| P3 | 락 대신 **임대(lease)** | 락에 소유 PID·시작시각·만료시각을 넣고, 만료·PID 사망이면 자동 회수 |
| P4 | 결과는 **원자적 + 영수증** | `.part`로 쓰고 검증 후 rename, 실행마다 manifest |
| P5 | 실패는 **분류 후 처리** | 일시(재시도) / 외부제한(냉각·우회경로) / 환경(자가치유) / 치명(격리+알림) |
| P6 | 사람 호출은 **마지막 + 구체적** | "PC2 Gemini 계정2 재로그인 필요" 처럼 할 일 1개로. 그 사이 다른 작업은 계속 |
| P7 | 자동 튜닝은 **범위 안에서만** | 시간·간격·동시성만 자동 조정. 발송·결제·계정 생성·차단 우회는 자동화 금지 |

## 4. 막힘 사다리 — "멈춰서 시간 낭비" 금지 규칙

모든 실패는 아래 사다리를 **자동으로** 한 칸씩 오른다. 각 칸에 시간 예산이 있고, 예산이 끝나면 다음 칸.

| 칸 | 동작 | 예산 | 예시 |
|---|---|---|---|
| L0 즉시 재시도 | 같은 단계 1회 재시도 | 즉시 | 일시적 UIA 오류 |
| L1 백오프 재시도 | 1분 → 5분 → 15분 (지터 ±20%) | 최대 3회 | 네트워크·5xx·429 |
| L2 **옆으로 비키기** | 이 작업을 `DEFERRED`로 큐 뒤로, **다른 작업 진행** | 즉시 | 특정 사이트 냉각 중 |
| L3 자가치유 | 고아 락 회수, 앱/Edge 재시작, 세대 리셋, 네트워크 재연결 | 10분 | G01·G04·G10·G11 |
| L4 대체 경로 | 공식 API·다른 도구·다른 시간대로 전환 | 작업 정의에 따름 | §6, §8 |
| L5 격리 + 알림 | `QUARANTINED` + 사람에게 할 일 1개 알림. **다른 작업은 계속** | — | 재로그인, 캡차, 결제 |

규칙:
- 같은 원인으로 L5에 3번 오르면 그 작업 유형을 24시간 **자동 비활성** (같은 실수 반복 금지).
- 큐에 실행 가능한 작업이 하나도 없으면 "유휴" 상태를 기록하고 15분마다 재평가 (멈춤 ≠ 유휴: 유휴는 이유가 기록됨).
- **멈춤 판정**: 작업이 `RUNNING`인데 진행 신호(heartbeat 증가, 출력 파일 크기 증가)가 예산의 2배 동안 없으면 kill → L3.

## 5. 감독자(Supervisor) — 새로 추가하는 핵심 부품

### 5.1 구성
```
supervisor.py (보조 PC, 로그온 시 자동 시작 + 작업 스케줄러 5분마다 "살아있나" 재기동)
 ├─ heartbeat.json      : 30초마다 갱신 {ts, cpu, ram, disk_free, net, current_job, queue_len}
 ├─ queue/              : 작업 = 파일 1개, 상태 전이는 rename으로 원자 처리
 │   READY → LEASED → RUNNING → DONE | DEFERRED | FAILED | QUARANTINED
 ├─ leases/             : 작업별 임대 (G01·G04 해결)
 ├─ checkpoints/        : 단계별 완료 표시 → 이어하기 (G05)
 ├─ diag/               : 진단 로그 (G21), 일자별 순환 (G17)
 └─ notify              : 알림 발송기 (§5.4)
```
메인 PC에는 `overseer`가 heartbeat.json을 2분마다 읽는다. 5분 이상 갱신 없으면 → WinRM으로 감독자 재기동 → 실패 시 알림 "보조 PC 응답 없음".

### 5.2 상태 머신 (기존 AI 운영 마스터 v3.0과 정렬)
`READY → LEASED → RUNNING → GENERATED → QA_PASSED → DONE → VERIFIED → LEARNED`
실패: `RETRYABLE_FAIL`(L1) / `DEFERRED`(L2) / `FATAL_FAIL` / `QUARANTINED`(L5) / `UNKNOWN_OUTCOME`(G02)

### 5.3 부팅·복구 루틴 (재부팅·정전 후 자동 실행)
1. 시간 동기화 → 오차 확인 (G12)
2. 디스크·메모리·네트워크 점검 (G13·G14)
3. 고아 락·리스 회수 (G01·G04)
4. `RUNNING`으로 남은 작업 → `UNKNOWN_OUTCOME` → 체크포인트부터 재개 (G02)
5. Edge 세대 리셋, 소유 탭 레지스트리 정리 (G10·G11)
6. 스모크 테스트 observe 1회 → 통과 시 큐 재개, 실패 시 알림
7. "복구 완료: 재개 n건 / 격리 m건" 알림

### 5.4 알림
- 채널 1개(사장님 선택: 텔레그램 봇 / 메일 / 슬랙 등). **긴급**(정지·보안·재로그인) 즉시, **일반**은 하루 1회 요약(09:00).
- 같은 내용 알림은 1시간에 1번까지만(알림 폭탄 방지).
- 알림 본문 = 증상 1줄 + 영향 + 필요한 조치 1개 + 그동안 계속 도는 작업.

## 6. 구글·네이버 제한 대응

### 6.1 감지 신호
| 신호 | 판정 |
|---|---|
| HTTP 429 / 503 + Retry-After | 속도 제한 |
| "비정상적인 트래픽", reCAPTCHA, 네이버 자동입력 방지 화면 | 봇 의심 차단 |
| 정상 200인데 결과 0건이 연속 3회 (평소 평균 대비) | **조용한 차단** 의심 |
| 로그인 페이지로 리다이렉트 | 세션 만료 (§8 G1) |

### 6.2 대응 (도메인별 서킷 브레이커)
1. **열림(OPEN)**: 해당 도메인 요청 즉시 중단 → 냉각 30분 → 2시간 → 6시간 (단계 상승)
2. 그동안 **다른 도메인·다른 작업 진행** (L2) — 수집 전체를 멈추지 않는다
3. **공식 경로로 전환** (L4): 네이버 검색 오픈 API(일 25,000회), 네이버 데이터랩 API, YouTube Data API, Google Programmable Search / Gemini API
4. 반열림(HALF_OPEN): 냉각 후 1건 시험 → 성공 시 속도 50%로 재개 → 점진 복구
5. 캡차 화면은 **풀지 않는다** → `QUARANTINED` + 알림
6. 일일 예산: 도메인별 요청 상한을 두고, 상한 70% 도달 시 저녁·새벽 시간대로 나머지 분산

### 6.3 설계에 넣지 않은 것 (명시)
- **A17 프록시 IP 순환으로 차단을 피해 수집을 계속하는 방식은 넣지 않았습니다.** 구글·네이버의 자동화 차단을 의도적으로 우회하는 것이라 약관 위반이고, 걸리면 계정·회선 단위 영구 차단으로 번져 맛가득 스마트스토어·유튜브 계정까지 위험해집니다. 캡차 자동 풀기도 같은 이유로 제외.
- A17은 대신 **§7 와이파이 장애 시 백업 회선**으로 씁니다. 전환 조건은 "링크·DNS 장애"뿐이고, "차단당함"은 전환 조건이 아닙니다.

## 7. 네트워크(와이파이) 장애 대응

| 상황 | 감지 | 자동 조치 |
|---|---|---|
| 와이파이 끊김 | 30초마다 게이트웨이 ping + DNS 조회 2곳 | 무선 어댑터 재연결 1회 → 실패 시 A17 USB 테더링으로 전환 |
| 회선은 살았는데 인터넷 불가 | 게이트웨이 OK, 외부 DNS 실패 | 공유기 문제로 판단 → 테더링 전환 + 알림 |
| A17 데이터 소진·발열 | 테더링 트래픽 일일 상한 | 상한 도달 시 대용량 작업(영상 다운로드 등) `DEFERRED`, 텍스트 작업만 |
| 복구 | 와이파이 정상 5분 지속 | 원래 회선으로 복귀, 테더링 해제 |

| 완전 오프라인 | 위 모두 실패 | 오프라인 가능한 작업(로컬 변환·받아쓰기)만 진행, 온라인 작업은 큐 대기 |

권장: 보조 PC는 가능하면 **유선 LAN을 1순위**, 와이파이 2순위, A17 3순위.

## 8. AI 관문 — 제미나이(구글 계정 1·2·3, 아르곤 보통 모델) · 노트북LM

### 8.1 작업 전 관문 (모두 통과해야 실행)
| 관문 | 확인 내용 | 실패 시 |
|---|---|---|
| G1 세션 | 로그인 상태, 로그인 페이지 리다이렉트 없음 | 해당 계정 `NEEDS_LOGIN` → 다음 계정 or API, 알림 |
| G2 계정 | 화면의 계정 라벨 = 작업에 지정된 계정 | 계정 혼선 → 실행 금지 |
| G3 모델 | 모델 라벨 = **지정 모델(아르곤 보통)**. 다른 모델로 몰래 바뀌었으면 실행 금지 | `MODEL_MISMATCH` → 모드 메뉴로 재선택 1회 → 실패 시 다음 경로 |
| G4 한도 | "한도 도달/잠시 후 다시" 배너 없음 | `QUOTA` → 리셋 시각 기록, §8.2 |
| G5 입력 | 입력 길이·첨부 수가 한도 이내 | 자동 분할 |
| G6 응답 완결 | 생성 중 표시 사라짐 + 마지막 문장 완결 + 최소 길이 | 중단 응답 → "계속" 1회 → 실패 시 재요청 |
| G7 결과 검증 | 작업별 형식 검사(JSON 파싱, 필수 항목, 금지어) | 실패 → 재요청 1회 → 격리 |

### 8.2 경로 우선순위 (실패 시 순서대로)
1. 지정 계정 + 아르곤 보통 모델 (웹)
2. 같은 계정, 한도 리셋까지 **다른 작업 먼저** (L2)
3. 공식 Gemini API (사장님 API 키·결제 한도 안에서) — **무인 자동화에는 이 경로가 가장 안정적**
4. 계정 2 → 계정 3 전환 ⚠️ **사장님 결정 필요**: 로그인 만료·장애 때 전환은 문제없지만, *사용 한도를 넘기려고* 계정을 돌리는 것은 구글 약관상 한도 회피로 보일 수 있어 세 계정이 함께 제한될 위험이 있습니다. 권장안은 **계정마다 작업 종류를 고정 배정**(예: 1=대본, 2=리서치, 3=노트북LM)하는 것.
5. 모두 불가 → `DEFERRED` + 다음 리셋 시각에 자동 재개

### 8.3 노트북LM 전용 관문
| 항목 | 방어책 |
|---|---|
| 소스 업로드 | 업로드 후 "처리 완료" 표시까지 대기 예산 5분 → 초과 시 재업로드 1회 |
| 소스 수·노트북 수 한도 | 작업 전 남은 수량 확인 → 부족하면 오래된 노트북 정리 대상 목록만 만들고 **삭제는 승인 후** |
| 오디오 개요 등 긴 생성 | 생성 시작 시각 기록, 20분마다 확인, 60분 초과 → 실패 처리 후 다음 작업 |
| 다운로드 결과 | 파일 크기·재생 길이·해시 기록, 0바이트·잘린 파일 감지 |
| 답변 근거 | 인용(출처 번호)이 없는 답변은 `UNVERIFIED` 표시 |

> "아르곤 보통 모델"이 화면에 표시되는 정확한 라벨 문구를 알려주시면 G3 검사 문자열로 고정하겠습니다.

## 9. 결과 데이터 — `K:\스크롤 데이터` "제대로 되는 패턴" 판정

### 9.1 올바른 패턴 기준 (데이터 계약)
| 항목 | 기준 |
|---|---|
| 폴더 | `K:\스크롤 데이터\<출처>\<YYYY-MM-DD>\<run_id>\` — 날짜·실행 단위로 분리 |
| 파일명 | `<출처>_<키워드>_<YYYYMMDD-HHMMSS>_<순번>.jsonl` 처럼 규칙 1개 |
| 쓰기 | `.part`로 쓰고 끝나면 rename (중간에 끊겨도 반쪽 파일이 정상 파일처럼 보이지 않음) |
| manifest | 실행마다 `manifest.json`: 시작·종료, 요청 수, 성공·실패·차단 수, 레코드 수, 파일 해시 |
| 레코드 | 필수 필드(수집시각, 출처 URL, 고유키, 본문) + 고유키로 중복 제거 |
| 완결성 | 레코드 수 / 기대 수 ≥ 95% 아니면 `PARTIAL` |
| 이상 감지 | 0바이트 파일, 남은 `.tmp/.part`, 파싱 실패, 같은 내용 중복, 날짜 공백(수집 안 된 날) |

### 9.2 점검 방법
보조 PC에서 1회 실행 (읽기 전용, 아무것도 안 바꿈):
```
python scan_scroll_data.py "K:\스크롤 데이터" > scan_report.json
```
`scan_report.json`을 보내주시면 위 기준과 대조해서 **패턴 판정 + 개선점**을 이 절에 채웁니다. 스크립트는 `tools/scan_scroll_data.py`.

## 10. 자기 튜닝 루프 (24시간 운영하면서 스스로 좋아지는 구조)

```
측정(매 작업) → 집계(매일 03:00) → 후보 조정값 생성 → 다음날 일부 작업에 시험 적용
 → 성공률·속도 비교 → 나아지면 LOCKED_BASELINE 승격 / 나빠지면 BLACKLISTED_FAIL 기록 후 원복
```
- 자동 조정 대상(범위 고정): 타임아웃, 백오프 간격, 도메인별 속도, 작업 시간대, 동시 실행 수, 재시도 횟수.
- 자동 조정 금지: 계정 전환 정책, 외부 발송·게시, 결제·쿠폰, 삭제, 보안 설정.
- 기록 위치: 로컬 `tuning/registry.json` (상태 표기 LOCKED_BASELINE / CANDIDATE / BLACKLISTED_FAIL — 기존 관리시트 체계와 동일) → 검증된 것만 Notion KB 승격.
- 한 번 BLACKLISTED_FAIL 된 조정값은 다시 시도하지 않음.
